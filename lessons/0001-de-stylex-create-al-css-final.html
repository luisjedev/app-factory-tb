De stylex.create al CSS final

Objetivo: poder narrar el build completo y saber por qué los plugins pertenecen a las apps, mientras la API StyleX pertenece a @repo/ui.

Abrir referencia rápida Fuente primaria: StyleX + Next.js

1. La distinción fundamental

AutoríaStyleX declara

En packages/ui/src/button.tsx, describes estilos como objetos JavaScript.

Compilación JSBabel transforma

El plugin reconoce llamadas StyleX y las sustituye por datos precompilados.

Compilación CSSPostCSS reúne

El plugin recopila las reglas y sustituye el marcador @stylex.

BuildNext empaqueta

Turbopack ejecuta ambas pipelines y produce los artefactos de cada app.

OrquestaciónTurborepo coordina

Lanza y cachea los scripts; no entiende ni transforma StyleX.

Babel se define oficialmente como un compilador de JavaScript cuyos plugins aplican transformaciones al código. PostCSS, en cambio, parsea CSS a un AST que sus plugins modifican. Son herramientas parecidas en el patrón —parsear → transformar → emitir—, pero trabajan sobre entradas y resultados distintos (Babel, PostCSS).

StyleX hace dos trabajos de compilación relacionados: el plugin Babel cambia el JavaScript y produce información sobre reglas; el plugin PostCSS usa la misma configuración para recopilar esas reglas y generar la hoja CSS. La documentación lo describe como una separación entre transformación de JS y generación de CSS (StyleX PostCSS).

Por eso apareció el primer error.

stylex.create() llegó sin transformar al prerender. La función runtime está diseñada para protestar: esa llamada debía desaparecer en el build.

3. ¿Por qué se configura en cada app?

packages/ui no tiene actualmente un script que produzca una librería compilada. Exporta directamente src/*.tsx. Quien crea un artefacto desplegable es apps/web o apps/docs, mediante next build.

Por tanto, la app debe conocer:

  • cómo transformar el TSX que importa: babel.config.js;
  • dónde buscar todas las reglas: postcss.config.js;
  • dónde insertar el CSS generado: @stylex;;
  • cómo incluirlo en todas las rutas: import de globals.css en el layout.

Turborepo no tiene una configuración StyleX porque solo encuentra scripts llamados build, calcula su orden y los ejecuta. La compilación interior pertenece a Next.js (tareas de Turborepo).

4. Regla para ubicar dependencias

Declara una dependencia en el paquete que la importa o la ejecuta.

pnpm mantiene el acceso estricto por paquete aunque use enlaces dentro del workspace (pnpm workspaces).

LugarNecesitaPorque
packages/ui@stylexjs/stylex en dependenciesSus componentes lo importan al escribir código.
packages/ui@stylexjs/eslint-plugin en devDependenciesSu propio script de lint ejecuta esas reglas.
Cada app@stylexjs/babel-plugin en devDependenciesSu build transforma JS/TSX, incluido UI.
Cada app@stylexjs/postcss-plugin en devDependenciesSu build genera el CSS final.
Cada appautoprefixer en devDependenciesSolo porque su PostCSS config lo ejecuta.

Matiz: los plugins Babel/PostCSS que hoy aparecen también en packages/ui no son necesarios para este modelo de “exportar fuente y compilar en la app”. Sí serían necesarios allí si UI tuviera un build independiente que emitiera JS y CSS ya compilados.
