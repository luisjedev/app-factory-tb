¿Es viable basar el sistema en StyleX?

Sí, para un monorepo React con apps Next.js y Vite, siempre que tratemos StyleX como un contrato de compilación por app, no como una librería que funciona solo por instalarla.

← Lección 2 Matriz de compatibilidad Fuente primaria: StyleX + Next.js

1. Separa las capas antes de comparar herramientas

La confusión aparece cuando llamamos “compilador” a todo. En realidad cada capa responde una pregunta distinta:

APIStyleX

¿Cómo declaramos, componemos y tipamos los estilos?

TransformaciónPlugin de Babel

¿Cómo desaparecen stylex.create() y otras llamadas estáticas?

IntegraciónPostCSS o unplugin

¿Cómo entra StyleX en el build y cómo se reúne su CSS?

BundlingTurbopack o Vite

¿Cómo se procesa y empaqueta la aplicación completa?

OrquestaciónTurborepo

¿Qué apps se construyen, en qué orden y qué resultados se cachean?

Idea clave: unplugin no significa “StyleX sin Babel”.

@stylexjs/unplugin@0.19.0 declara como dependencias @babel/core y @stylexjs/babel-plugin. En Vite, unplugin encapsula la integración; no reemplaza el compilador oficial de StyleX. Puedes comprobarlo en el manifest oficial del paquete.

Por eso pueden coexistir varios motores: Next usa SWC para transformaciones internas de JSX/TSX y compatibilidad JavaScript, pero activa Babel cuando encuentra tu configuración; el plugin de StyleX realiza entonces su transformación especializada. La documentación de Turbopack describe expresamente esta convivencia.

Evidencia de este repositorio.

Se ejecutó pnpm turbo run build --force: web y docs compilaron correctamente con Next 16.3.0, Turbopack y la configuración Babel externa. Esto demuestra la ruta Next actual; todavía no demuestra la ruta Vite.

3. El contrato entre @repo/ui y las apps

Ahora mismo @repo/ui exporta directamente archivos de src. Es un modelo de fuente compartida: la biblioteca no entrega un bundle independiente; cada consumidor transforma el código que importa.

ResponsableDebe mantenerNo debería asumir
@repo/uiAPI runtime, tipos, tokens, temas, componentes y reglas ESLintQué bundler usará cada app
App NextBabel, PostCSS, include, @stylex; y CSS raízQue UI ya venga compilada
App Viteunplugin, orden de plugins, asset CSS y HMRQue Vite transforme StyleX por sí solo
TurborepoTareas, outputs y cachéCómo funciona StyleX internamente

Si Vite trata un paquete StyleX como dependencia preempaquetada y no ve su fuente, el adaptador ofrece externalPackages para forzar su transformación. No hay que añadirlo por intuición: hay que comprobar primero si @repo/ui queda cubierto y usarlo si el build o HMR lo omiten (opciones de unplugin).

StyleX está todavía en versiones 0.x. En este repositorio todos sus paquetes usan ^0.19.0; conviene mantenerlos alineados y agrupar sus actualizaciones. Un cambio de integración debe pasar, como mínimo, por lint, tipos, build de todas las apps y una prueba visual de temas.

5. Opciones que existen, pero no son equivalentes

OpciónQué resuelveDecisión recomendada
Babel + PostCSSMáxima compatibilidad cuando el bundler no ofrece el hook adecuadoUsarlo en Next
StyleX unpluginIntegra transformación y agregación con bundlers modernosUsarlo en Vite React
runtimeInjection: trueEvita configurar extracción CSS, pero conserva compilación Babel e inyecta en runtimeSolo desarrollo o diagnóstico
Compilador StyleX sobre SWC comunitarioBusca eliminar Babel de la transformación StyleXNo adoptarlo como base todavía
Precompilar @repo/uiReduce trabajo de los consumidoresReevaluar solo si UI se publica fuera

El propio equipo de StyleX define al plugin Babel como la pieza central que extrae estilos y que luego usan las integraciones de bundler (Introducing StyleX). Cambiarlo por una implementación comunitaria aumenta la superficie que tendríamos que probar y mantener.

6. Veredicto condicionado

Verde

Adoptar

Apps React/TSX, paquetes privados del monorepo, CSS estático y adaptadores oficiales por app.

Amarillo

Probar antes

Vue/Svelte, paquetes externos sin compilar, microfrontends o cambios frecuentes de bundler.

Rojo

No basarlo todo

Si exigimos cero Babel, cero configuración por app o CSS completamente dinámico.

Conclusión para este monorepo: viable con riesgo controlable.

Mantendría @repo/ui como fuente StyleX compartida, Babel/PostCSS en cada app Next y unplugin en cada app Vite React. Antes de declarar compatibilidad total, añadiría una app Vite mínima que consuma botón, tokens y tema oscuro, y la convertiría en prueba permanente de CI.
